# Backend handover checklist

What a real backend must enforce by itself. One line per rule, each with the
function in the mock that shows the intended behaviour and the test that holds it.

This restates `docs/api-contract.md` (sections 0 to 10, Appendix A and B) and the
plans in `docs/superpowers/plans/`. It adds no rule of its own. Where the contract
and the code disagree, the rule is listed under "Discrepancies" at the end, and
this file does not pick one. The code and its tests are the record, as the
contract says of itself.

How to read a line: **Mock** is `file › function`, **Test** is `file › "describe or it"`,
paths relative to the repo root. "No test" means exactly that. A rule marked
**Gap** is one the mock leaves to the screen, so a backend that copies the mock
copies the gap.

The mock has no identity. `orgId` and `advocateId` are arguments the screen
passes. A backend derives both from a server-verified session and never takes them
from the request.

## 1. Access and organisation scoping

- [ ] Derive the organisation and the advocate from the verified session, never from a request field. Mock: every `lib/api/*` function takes the id as an argument. Test: none, the mock cannot hold it.

Test: `lib/api/client/documents.test.ts` › "returns the same nothing for another organisation's document, as that organisation, and for one that is not there".
- [ ] The same not-found for another organisation's consultation request as for one never made, and nothing is paid. Mock: `lib/api/client/consultations.ts` › `payClientConsultation`. Test: `lib/api/client/consultations.test.ts` › "is the same refusal for another organisation's request as for one that is not there, and pays nothing".

- [ ] Payout lines are scoped by the authenticated advocate. Mock: `lib/api/consultations.ts` › `getPayoutStatement`. Test: `lib/api/payouts.test.ts` › "is each advocate's own, and another's lines are not in it", "reaches another advocate's request no more than a made-up one: the same not-found".
- [ ] Organisation membership, roles, who may invite or remove, and protection of the last owner. Mock: `lib/api/account.ts` › `inviteMember`, `removeMember` change an in-memory list only. Test: `lib/api/account.test.ts`. Gap: all of it is backend work (contract 10.2).

Test: `lib/api/summaries.test.ts` › "is not available before sign-off, and the answer carries nothing of the content", "stays unavailable before sign-off even if a summary is stored for the document", "is not shown against a text that has changed since it was written".

## 4. The citation gate

- [ ] A citation is verified or blocked, with no third state, and matching is exact after normalising whitespace and case only. A near-miss is blocked, and there is no fuzzy matching. Test: `lib/citations.test.ts` › "blocks a near-miss, every one of them", "normalises whitespace and case and touches nothing else", "blocks empty input", "blocks a ref the corpus does not hold".
- [ ] The gate runs again at every snapshot, on the working copy and the snapshot alike. A blocked citation becomes verified only by matching the corpus, and a verified one that no longer matches becomes blocked. Mock: `recordVersion`; `lib/citations.ts` › `recheckCitation`, `recheckFindings`. Test: `lib/citations.test.ts` › "running the gate again on the record › …"; `lib/api/documents.test.ts` › "runs the citation gate again, so a citation the corpus no longer holds is blocked".

Test: `lib/api/advocate-gates.test.ts` › "adding a finding › takes no word of the caller's about whether a citation is verified", "enters the record open, marked as added by an advocate, whatever it arrived as".
- [ ] Only a blocked citation can be withdrawn, with a non-blank note, recorded with who, when and why. It stays on the record as blocked and is never relabelled verified. Mock: `withdrawCitation`. Test: `lib/api/advocate-gates.test.ts` › "withdrawing a source › …" (three tests).
- [ ] A finding cannot be settled while a citation is blocked and not withdrawn, and a finding with no verified source can be settled only with the advocate's note. - [ ] The pre-gate fabrication rate is blocked typed attempts over all typed attempts, and says "None yet" when there is nothing to divide. Mock: `lib/api/metrics.ts` › `getMetrics`. Test: `lib/api/metrics.test.ts` › "read the fabrication rate and the blocked log from the attempts, as typed".

Mock: `getMetrics`. Test: `lib/api/metrics.test.ts` › "say there is no source for the triage override rate and the corpus-currency lag, and give no number".

## 6. Billing and idempotency

- [ ] Every write is one transaction. A failed call leaves no partial state and the client can try again. Mock: every write checks the failure switch before it writes. Test: `lib/api/execution.test.ts` › "changes nothing when it fails, and works again afterwards"; `lib/api/privacy.test.ts` › "changes nothing when it fails".
- [ ] Pay the document fee once. A document that already has a payment comes back as it is, and the check precedes the failure path. Mock: `payFee`. Test: `lib/api/documents.test.ts` › "is paid once, at its tier's flat fee, however many times Pay is pressed".
- [ ] Pay a consultation once. Mock: `payConsultation`. Test: `lib/api/consultations.test.ts` › "paying › moves money only here, once, however many times it is pressed".
- [ ] Request a consultation once. The same question on the same document while `requested` returns the one request, and a failure creates nothing. Mock: `requestConsultation`. Test: `lib/api/consultations.test.ts` › "is made once, however many times the button is pressed", "creates nothing when it fails…". Gap: the mock's key is the question text. Use a client-supplied idempotency key and a unique constraint inside a transaction (Appendix B item 9).
- [ ] A create-draft request needs an idempotency key, so a double submit creates one draft. Mock: `lib/api/client/documents.ts` › `createClientDraft` makes a draft for every call it is given, and the screen guards the press instead (`lib/reentry.ts` › `runExclusive`, used by `components/marketing/deal-prompt.tsx` and `components/domain/intake-wizard.tsx`). Test: `lib/reentry.test.ts` holds the guard; the two presses were checked in a browser (one draft each), not by a test. The mock has no key and none should be invented there: it belongs to the real request, and a guard in a page does not hold across tabs or retries.

## 8. State changes a backend must guard (audit of the client write functions)

The audit read every client write function for a state change with no state precondition. The ones that have one are in the sections above. The rest, and what a backend must do about them, are below. Each says whether the mock already refuses it.

- [ ] Starting analysis must refuse any status but `draft`, or accept `analysing` as an idempotent no-op. Mock: `lib/api/documents.ts` › `startAnalysis` returns any other status unchanged, silently. Test: none. Open in the mock.
- [ ] Ticking a checklist step must refuse a document with no applicable steps, and the internal write must check for a recorded sign-off itself (Appendix B item 8). Mock: `toggleExecutionStep` has neither, and `[].every(...)` is true, so with no applicable steps any tick on a `settled` document would make it `executed`. Real sign-off always builds steps, so this is not reachable today. Test: none. Open in the mock.
- [ ] An unknown checklist step kind must be refused. Mock: `toggleExecutionStep` and `attachEvidence` do nothing and return the document. Test: none. Open in the mock.
- [ ] The training opt-in must be a boolean, checked at the server. Mock: `lib/api/privacy.ts` › `setTrainingOptIn` does not check it at runtime. Test: `lib/api/privacy.test.ts` covers the changes, not the type. Open in the mock.
- [ ] A new draft must be validated at the server against the same rules as the intake form (title, type, value). Mock: `createClientDraft` trusts its input. Test: `lib/api/client/draft.test.ts` covers ownership and ids only. Open in the mock.
- [ ] **Analysis must advance on a timer or a job, never on a read.** Mock: `reconcileAnalysis` moves `analysing` to `awaiting_payment` and assigns the tier whenever a document is read (`getDocument`, `listDocuments`), so a GET changes state. A backend runs screening as a job and a read changes nothing. Test: `lib/api/documents.test.ts` › "the snapshot written when the first pass finishes › …" holds the result, not where it runs.
- [ ] A deletion request needs a processed state, after which withdrawal is refused. Mock: `withdrawDeletion` always succeeds, because no such state exists, although its comment says "until it is processed". **Open for counsel** (contract 10.5): what "processed" is, and what deletion removes and keeps.
- [ ] A client's second press is guarded by the screen, and the API refuses a repeat. A backend keeps the refusal, with an idempotency key where a repeat should succeed (section 6). Mock: `app/(client)/documents/[id]/page.tsx` › `handleRespond` (ref guard); the API refusal in `respondToChanges`.
